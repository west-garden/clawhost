ClawHost User Portal — Architecture

Overall system architecture with data flow

System Architecture
🌐 Browser
• React pages
• NextAuth session cookie
• Never sees ClawHost tokens
→
⚡ Next.js Server
• NextAuth.js (email/pw + OAuth)
• Server Actions / API Routes
• Stores: users, app_tokens
• Calls ClawHost API server-side

DB: PostgreSQL (shared or separate)
→
🔧 ClawHost API
• Existing REST API (unchanged)
• App multi-tenancy model
• Bot CRUD + lifecycle
• K8s orchestration

DB: PostgreSQL (apps, bots)
→
☸️ K8s Cluster
• OpenClaw Pods
• Per-bot Service
• Shared PVC
Data Flow:
1. User registers → NextAuth creates account → Server calls ClawHost Admin API to create App
2. User creates bot → Server uses stored app_token to call ClawHost POST /bots
3. User starts bot → Server calls ClawHost POST /bots/:id/start → K8s Deployment created
4. User accesses bot WebUI → Redirect to ClawHost proxy with bot access_token
🔒 Security: Browser ↔ Next.js uses session cookie only. ClawHost admin_token and app_tokens never reach the browser.
